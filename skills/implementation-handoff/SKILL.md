# 实现决策交接

让用户理解最终实现如何工作、代理做了哪些重要选择，以及这些选择的影响。交接依据当前任务的实际代码和验证结果，默认使用简体中文。

## 过程同步与交付时机

在工作过程中保留重要取舍、意外发现和验证结论，最终按结果组织交接，避免复述完整操作流水账。

- **先确认再实现**：拟改变用户已确认的行为、缩减支持范围或引入重要新约束，且现有授权不能确定这一选择时，说明具体取舍并确认；已有明确授权不重复询问。
- **告知并继续**：方案明显变重、发现意外依赖或成本，但工作仍在授权范围内时，及时说明影响并继续。
- **最终交接**：整次任务要求的编码、review、问题修复、E2E 及其他适用验证结束后，整理最终状态。review 或验证引起后续修改时，交接覆盖修改后的结果。
- 只执行用户要求和适用项目规则规定的流程；本 skill 不额外强制 review、E2E、type-check、lint、提交或部署。
- 待完成的 review 或测试不能当作任务已完成。任务被阻塞、中断或用户要求提前停止时，报告已完成内容、阻塞和未验证项；用户要求阶段性交接时明确标注阶段性状态。
- 完成 coding 后的单独 commit/push 请求，若没有新的实质修改，不重复生成相同交接文档。用户要求补写或重新交接时按其指令执行。

## 选择交接深度

默认先判断能否在简短回复中清楚交代结果、关键机制、取舍和验证。能说清且没有重要语义变化时直接回复；仅涉及多个文件、复用跨模块调用或花较多时间排查与测试，不足以触发留档。不用行数、文件数或“bugfix”标签机械分类。

**只在对话中交接**：局部且容易理解的修改，没有重要的新机制、取舍或行为约束，例如文案纠正、样式微调、小配置调整、复用现有逻辑的入口补齐，以及恢复既定行为的小缺陷修复。简述结果、必要的实现细节、实际验证和限制，不强行填满模板。小修复涉及相关历史、权限或存储代码时，先区分是恢复已有约定，还是实际改变约定。

**生成详细文档**：新增或改变了值得长期追溯的关键机制、重要行为边界或技术取舍，例如需要解释多个状态间的协调、具有实际代价的方案选择，或会持续影响维护与排障的复杂实现。即使改动很少，只要实质改变权限、数据持久化、撤销语义或兼容范围，仍应生成文档。明确存在这些影响时不能仅因简短回复能概括结论而省略文档；普通改动处于临界情况时，优先对话交接。

由代理根据本次任务判断，无须每次询问用户是否留档。用户指定的文档要求优先。纯咨询、只读分析、没有实质实现变化的操作通常直接回复。

## 详细文档的内容

先核对任务目标、最终改动及实际验证记录。只读与本次工作有关的差异和关键实现，排除用户及其他任务的无关改动。区分已确认事实、基于代码的推断和未验证行为，不把计划或测试用例名称当作完成证据。

以下是内容核对维度，不是必须逐项展开的章节模板。选取影响用户理解和后续维护的部分，合并相关内容、略去无关维度，避免为填满模板拉长文档。

1. **目标与最终结果**：解决的问题、实际完成范围、与原需求的偏差，以及用户可见行为。主动揭示不同入口、平台、权限或状态下的差异、默认行为和降级路径。
2. **关键实现**：入口及关键调用链、模块职责、复用和新增的机制；解释重要机制怎样工作、为什么采用，以及它带来的影响。附少量关键代码位置供追溯，不逐个罗列所有改动文件。
3. **状态与边界**：相关状态归属、数据流转、持久化及清理时机；适用时说明并发、取消、重试、部分成功、撤销和迟到结果处理，以及资产关联、共享状态副作用和用户／项目隔离。涉及接口、依赖、后端配合、埋点或错误诊断时说明对应变化和口径，不自动扩充这些功能。
4. **重要决策与代价**：明确标出用户指定和代理自行决定的重要选择；说明有实际意义的替代方案、选择依据、兼容与维护代价。不要编造从未评估过的方案或声称用户批准了自行决定的细节。
5. **最重的部分**：按下一节分别解释技术复杂度和实际投入。
6. **验证与遗留**：归纳实际 review 发现及修复、测试／E2E 覆盖与结果、未验证场景、已知限制和剩余事项。说明检查针对哪个最终状态，区分通过、失败、未执行与环境阻塞；涉及后续改动的旧检查不能直接当作最终验证结果。

文档不保存凭据、剪贴板原始内容或无关用户数据。

## 图文组织与可读性

- 开头用短摘要说明最终变化、最重要的取舍或限制、验证结论；让读者先理解结果。随后展示关键机制，代码位置和完整追溯信息放在后部。
- 对多步骤流程、模块交互、数据流和状态变化，优先用 Mermaid 图作为主要说明：分支逻辑用流程图，异步协作与先后顺序用时序图，上传／撤销／重试等生命周期用状态图。通常一张主图即可，只有独立机制确有需要时再补图。
- 每张图只解释一个问题，标出关键分支、边界和本次变化，使用简短中文标签。复杂关系拆成几张可读的小图，避免把所有函数、字段和文件名塞进同一张图。
- 图后用短段落补充原因、代价和容易误解的细节，不逐节点复述。需要准确对照的入口差异、方案取舍或验证状态用紧凑表格；简短结论用文字，不为了图的数量强行绘图。
- 突出最重的部分及其原因，把必要的代码定位、验证细节与诊断证据放入后部参考区；避免整段日志、逐条命令和重复限制淹没主线。正文保留关键未验证项与风险。
- 图源使用 Mermaid 代码块，遵循全局图表样式与渲染检查规则。若实际阅读器不能显示 Mermaid，从源码渲染图片供阅读并保留源码；不以手绘图片代替图源。

## 解释最重的部分

这两项可能不同，必须分别判断；没有突出复杂点时直接说明，不为了模板夸大工作。

- **技术最复杂或风险最集中的部分**：指出具体机制或交互，解释困难来自哪些状态、不变量或依赖；说明如何控制风险，以及剩余代价。
- **实际投入最多的部分**：依据本次实际工作，说明主要精力花在实现、排查、兼容还是验证，以及原因。没有计时或可靠记录时使用定性描述，不编造工时、百分比或精确排名。
- **复杂度是否合理**：区分需求必需、现有架构带来和本次方案引入的复杂度；评价是否值得，说明确有依据的简化机会及其功能、性能或兼容代价。已有明显更简单的方案时如实说明，避免事后为实现辩护。
- 发现简化机会不自动扩大任务范围；本已授权的 review 和修复仍应完成，交接反映最终采用的方案。

## 文档位置与最终回复

- 所有项目的详细交接统一保存为 Markdown，按生成当天的本地日期分目录：`~/Documents/docs/implementation/YYYY-MM-DD/`，需要生成文档时再创建目录。
- 每次需要留档的最终交接都新建一份快照，保留旧报告。文件名使用 24 小时制的 `HHmm-项目-任务.md`，例如 `2026-10-16/1805-deevid-canvas-paste.md`；日期目录与时间前缀取同一生成时刻，同名时追加序号，不能覆盖已有文件。
- 标题标明任务，开头简要标明项目；仓库位置、生成时间（含时区）、可获取的分支、提交和相关未提交状态集中放在文末追溯区。提交与未提交改动并存时明确报告覆盖的状态；不为获得提交号而自动提交。
- 同一需求的后续交接可链接前一份报告，但新报告应独立说明当前结果。历史快照不因后续修改而被改写，也不自动复制进入项目仓库。
- 最终回复简要说明结果、最值得用户关注的技术决策或限制、最重的部分和验证状态，并提供文档的绝对路径 Markdown 链接。重要偏差或未解决问题仍需出现在回复中，不能只埋在文档里。
- 写完检查文档是否与最终实现一致，关键取舍是否遗漏，链接和路径是否可用。写入失败时明确说明，并在对话中完成必要交接，不声称文档已生成。
