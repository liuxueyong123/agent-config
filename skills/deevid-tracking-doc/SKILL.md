# Deevid 埋点文档

产出一份贯穿开发前后的中文埋点文档，让不读代码的人也能理解：**需要哪些事件、何时触发、何时不触发、有哪些参数、每种取值意味着什么**。事件名、字段名、枚举值及代码标识符保留英文。

## 文档写法与层级

- **一个事件占一个完整小节**。在“逐事件说明”中，用 4.1、4.2 等三级标题区分事件，内部用加粗标签组织触发、参数、复杂取值和例子，不再机械增加 4.1.1 等下级标题。省略可选章节时连续调整编号，读者在一个事件小节内就能查齐它的说明。
- **先用一句话说明事件记录什么，再用短表格和短列表展开**。一个段落或列表项只讲一个要点；出现多个条件、例外或结论时拆开，不用连续分号堆成长段落，也不把长段落塞进表格单元格。
- 标题和表头使用简洁、易懂的书面表达，如“埋点范围”“触发条件”“必填条件”“详细取值说明”“典型场景示例”；正文继续用具体动作和条件解释，不为了正式而堆砌术语。“参数来源与取值时机”指参数从哪里获取、在操作的哪个阶段读取，例如读取点击提交时的当前选项；事件触发时机描述何时记录事件，两者可能一致，也可能不同。
- **开头的事件总览保留“新增／复用／调整”**，同时简述触发时刻、次数或去重规则及口径确认状态，便于先判断本次涉及哪些变更；具体条件在对应事件小节展开。
- 正文使用用户看得见的动作和结果，如“用户点击 Try Now 后立即记录，切换模型失败也记录”。“去重”第一次出现时解释为“同一次展示只记录一次”；`helper`、`reporter`、`nullish`、闭包、mock 等实现术语留在技术附录。
- 触发条件用短列表，简单字段的类型、必填条件、来源、取值含义和缺失规则收在同一张参数表中；复杂枚举或动态值才展开字典与补充说明。简单事件保留含义、触发与次数、必要参数即可；复杂事件按需补取值字典和典型场景示例，不机械套用全部块。
- **共用口径按需出现**：仅提取多个事件确实相同的规则或业务参数；每个事件明确列出自己引用的共享字段与说明位置，差异在本事件内说清。没有共享内容和需要在正文解释的公共自动字段时，省略整个共用章节。
- 例子按“操作、是否记录、参数值”的顺序解释容易误解的规则，使用唯一示例编号供验收场景引用。验收表仍覆盖每个事件的正向与反向边界；已有例子可引用并补齐预期次数、参数及执行结果，不重复抄写操作步骤。
- **正文聚焦本次业务参数**。系统自动字段在正文只保留影响本次统计理解的说明；完整字段字典以链接引用，必要补充放附录。不因缺少公共字典而在每份功能文档里重建全量字段清单。
- 同一事实只详细解释一次，其他位置简短引用。没有内容的可选表格直接省略，不为每个事件机械生成“无专属参数”“无额外字典”等小节；已知限制和待确认项各集中一处。
- 不为缩短文档省略枚举含义、触发边界或待确认状态。除非用户要求指标设计，否则只简述分析用途和分析限制，不展开复杂的计算公式和归因方法。

## 范围与决定权

- **用户指定要记录的行为或事件，skill 不自行增加事件。** 用户可以只描述“记录生成按钮点击”，不必提供英文名称。若尚未指定范围，先询问范围；“给新功能写埋点文档”不等于授权设计完整漏斗。
- 在指定范围内，检查已有事件是否可复用，再建议事件名、触发条件、参数、取值及含义。将这些建议组成完整草案，集中呈现待决策项，**用户确认后才成为正式口径**；已有明确确认无需重复询问。
- 某个分析问题需要范围外事件才能回答时，只说明当前数据的分析限制，不将额外事件加入方案。用户之后明确扩展范围才补充。
- 此 skill 维护文档，不自行修改埋点代码、发送测试埋点或发布到外部文档平台。用户另行要求实施时，按该任务的代码工作流处理。
- 开发后保留已确认的预期契约，列出代码差异及建议，由用户决定改代码还是改文档；不得将实现偏差直接写成新的正式口径。

## 读取所需上下文

先定位用户指定功能的需求、已有埋点文档和相关代码；只读本次事件涉及的内容，不做全站埋点审计。能从仓库查明的信息不重复询问用户。

此 skill 安装在全局目录，服务于 Deevid 项目。下表及输出文档路径均相对于当前 Deevid 仓库根目录解析，不相对于 skill 安装目录；`assets/` 模板路径相对于本 skill。先从工作目录定位仓库根目录；若当前不在 Deevid 仓库且上下文未提供其位置，再询问项目路径，不把 Deevid 协议套用到其他项目。

| 需要确认的内容 | 本项目来源 |
| --- | --- |
| 埋点所有权、命名与接入约束 | `apps/frontend/lib/tracking/README.md` 的相关章节 |
| 事件名、字段类型与已有枚举 | `apps/frontend/lib/tracking/events.ts` 及其引用类型 |
| 值的转换、默认值、去重逻辑 | `apps/frontend/lib/tracking/business/` 下对应 helper 和测试 |
| 实际触发条件及分支 | 功能组件、Hook 或服务中的 helper 调用点及相关测试 |
| 自动补充字段与发送方式 | `apps/frontend/lib/tracking/reporter.ts`；需要核对传输时再读 `apps/frontend/lib/api/tracking.ts` 和 `apps/frontend/lib/tracking/types.ts` |

项目当前 `/event/report/batch` 的 `eventType` 只接受 `CLICK` 和 `EXPOSURE`。“点击、曝光、结果、离开”是业务语义，不是四个传输枚举；结果事件应核对同域先例，不能自行创造 `RESULT`。新功能事件按 tracking README 使用 `<module>_<action>` 和小写 `eventData.feature`；既有事件保留现有协议，不因本文档统一重命名或改造 `page_view` 等平台事件。

## 开发前：形成完整草案

1. 明确用户指定的行为、功能入口、适用人群及已有确认。按“新增／复用／调整”梳理事件；同一行为拆成多个事件也需要用户确认，不能借参数设计扩充范围。
2. 结合需求及代码，写清每个事件的业务含义、精确触发条件、不触发条件及去重边界。代码尚不存在时写设计建议，不编造现有实现。
3. 按下方参数规则补齐建议，复用同域已有口径。无法确定的规则保留为具名待确认项，说明推荐方案、理由和影响；不在正文中把猜测写成事实。
4. 以本 skill 自带的 [文档模板](assets/tracking-document-template.md) 为文档结构依据，生成完整草案；已有业务文档仅用于核对本次涉及的事实和口径。正文以中文业务说明为主，技术细节集中在附录。给用户一份简短的决策清单，等待集中确认；不要逐个事件反复打断。
5. 确认后更新同一份文档的口径状态。部分确认时明确哪些事件或字段已确认，未决部分仍保持草案；**口径已确认不代表已实现或已验收**。

用户指定输出位置时遵从；否则优先更新该功能的现有文档。无现有文档时沿用仓库先例，写入 `docs/superpowers/specs/YYYY-MM-DD-<feature>-tracking-spec.md`。模板中的占位说明应被实际内容替换，缺失信息转为明确的待确认项。

## 事件与参数必须说清的内容

- **触发**：写明哪个用户动作或业务状态、满足哪些前置条件、在什么时刻产生事件。区分点击意图、校验通过、请求发出、后端接受及任务最终成功；不要只写“操作时”或“成功时”。
- **不触发与次数**：按事件需要说明禁用或拦截、取消、重复渲染、重复点击、重新进入和请求重试等情况。曝光说明实际可见条件、去重对象和重置时机；若需可见比例或时长，应提出并确认具体阈值，不默认发明阈值。业务上不适用的场景无需凑齐。
- **参数目录**：每个业务参数写明英文名、中文含义、类型、必填条件、参数来源与取值时机。必填条件不能只写“视情况”；嵌套对象和数组需解释实际使用的子字段与元素结构。
- **取值字典**：有限枚举逐值列出含义和出现条件；布尔值解释 `true` 与 `false`。不要只列 `a / b / c` 或写“同代码”。固定值也说明含义；示例值不得冒充完整枚举。
- **开放值域**：ID 说明标识对象、来源和生命周期；数值说明单位、范围及零值含义；时间和耗时说明格式、起止点及单位；动态模型或配置值说明合法集合的权威来源和更新方式。无法穷举时明确这是开放值域，给出规则和有代表性的示例，不伪装成封闭枚举。
- **缺失语义**：区分省略、`null`、空字符串、`0`、`unknown` 及“不适用”，只允许实际契约支持的形式。不能为了填表而给所有字段增加默认值；非法值和未知值的处理也应有明确口径。
- **字段层级**：业务参数按事件列出或准确引用共享参数集，使读者能还原完整业务参数集合。公共自动字段的完整说明引用已有字典，必要的补充放技术附录，不要求研发在每个调用点重复传入；正文若用到公共 `session_id`，需说明它与业务会话的区别。
- **数据边界**：新增业务参数优先使用稳定枚举、数量和业务 ID，不默认采集原始 Prompt、联系方式、完整 URL、令牌或原始错误文本。描述现有采集行为时如实记录，发现问题单列，不未经授权改写现状。

## 开发后：核对同一份文档

沿“调用点 → helper → 字段定义／转换 → reporter”核对触发时机、分支覆盖、字段和值、去重和自动字段；类型中有定义不等于存在调用点，存在调用点也不等于已上线。

在附录逐事件列出预期、实际、证据位置、影响和建议，状态使用“代码一致／未实现／存在差异／无法核实”。将口径确认、代码核对和测试验收分别记录。只有代码检查就写“静态核对”，测试场景尚未执行就写“未执行”；不宣称生产数据可用或验收已通过。缺少运行环境、后端或数据平台证据时，明确未核实边界。

仅更新文档不自动执行应用检查或向真实环境发送事件。若用户要求运行验证，再按仓库验证策略选择最小相关测试。

## 交付前核对

- 事件集合与用户指定范围一致；新增命名和参数建议有确认状态，未确认项没有混入正式契约。
- 事件总览在开头展示新增／复用／调整；逐事件小节内部没有机械堆叠编号标题。简单字段在参数表中即可读懂，详细取值说明按需展开；共享字段引用明确，典型场景示例与验收场景没有重复抄写操作。
- 每个事件的说明均收在对应小节内；正文没有长篇技术解释、全量公共字段清单或仅换一种说法的重复段落。口径确认、实现核对与测试验收仍分别记录，不因压缩结构而合并。
- 每个事件都有可判定的触发和不触发条件；每个参数都能找到类型、取值规则与含义；同名字段在各事件中口径一致或明确解释差异。
- 参数示例符合正文定义，省略与 `null` 不混用；测试场景含预期事件、次数和关键参数，覆盖相关正向与反向边界。
- 分析说明仅基于范围内数据；涉及漏斗、去重人数或成功率时写清关联键、计数单位和分母，信息不足就标明不能可靠计算，不推导不存在的数据。
- 正文无需读代码即可理解；附录来源可追踪，差异未覆盖正式口径。检查修改文件的链接及 `git diff --check`，如实汇报文档状态和未决问题。
